# GLOBAL HEURISTICS (apply to every pick)

0. **WIN-PROBABILITY FIRST, EDGE SECOND** — ✅ **ENFORCED IN CODE + SIMULATED (2026-08-19)**. `scripts/win_simulator.py` / `POST :8001/simulate-ticket`, and **every `/predict` now returns a `win_simulation` block**. Three things this changed:
    - **Every match gets a win read, even a PASS.** A pick that fails the VALUE gate still has a win probability, and that number is shown rather than suppressed (Sabalenka −900 reads `PASS` on value and `87% — STRONG` on winning, both true, both printed).
    - **The verdict band is set by win probability ALONE** — `STRONG ≥60%` · `PLAYABLE ≥50%` · `THIN ≥35%` · `LOTTERY <35%`. EV is returned as `ev_pct` with `ev_is_secondary` beside it and **cannot change a verdict**. A +100% EV shot at 20% still prints LOTTERY (there is a test asserting exactly that). `rank_by_winning()` orders candidates by win% and uses EV only to break a tie.
    - **The linter trims by OUR win probability, not the book's price.** `slip_linter._win_prob` prefers the model's `prob` and only falls back to `1/decimal`. On a real 6-leg tennis slip this changed which legs got cut — price-ranking dropped Musetti (73.6%) and kept Keys (64.5%); model-ranking correctly drops Keys.
    - The simulator also reports the **near-miss distribution** and **risk of ruin**, because "how often do I land 5 of 6 and get paid nothing" and "does a normal losing run bust me" are the questions a bare EV number cannot answer.

    Original directive: among bets that clear the value gate, rank by WIN PROBABILITY first, then by edge. Favor likely winners over +EV longshots. A 65%-to-win pick at small +EV beats a 30% longshot at fat +EV — we are building a hit-rate record, not chasing variance. Only take a longshot when the edge is large AND the safer markets have no value.
    - **PICK-QUALITY GRADE (enforced in `edge_api.pick_quality`, surface it on every pick):** `LOCK` (≥70% to win + value, anchor-grade) · `PICK` (≥62% favourite with real edge, parlay-eligible) · `LEAN` (<62% — a soft favourite, NOT a lock: single or small stake, **NEVER a parlay anchor**) · `PASS` (no edge). This is the win-prob lens `edge_strength` lacks — `edge_strength` scores the EDGE only, so a thin-edge soft favourite (Kecmanovic ~56%, Navarro ~60% — the engine's only two misses on 2026-06-25) used to read like a lock. It can't anymore. Only LOCK/PICK anchor a ticket.
1. **VALUE GATE (not narrative)**: a bet only qualifies if its true win probability BEATS the bookmaker's devigged implied probability. No edge → PASS, do not force a pick. Never bet purely on "who will win" without that gap. (Then apply rule 0 to rank what's left.)
2. **CORRELATION STRESS TEST (SGPs)**: Only pair legs with MATHEMATICAL multiplier effect. If Leg A hits, does it make Leg B statistically more likely — or just emotionally more likely? Reject emotional correlation.
3. **JUICE FILTER**: Reject any parlay where cumulative vig exceeds 15%. ✅ **ENFORCED IN CODE (2026-08-19)** — `slip_linter.ticket_vig()`; `lint()` returns REJECT above `MAX_CUMULATIVE_VIG` (0.15). Vig needs BOTH sides of a market, so pass `opposite_decimal` on each leg; legs without it are counted as **UNMEASURED** and reported, never estimated (a fabricated vig is worse than a missing one). Linemate (rule 17) supplies both sides across up to 32 books.
4. **CLV (CLOSING LINE VALUE)** — ✅ **FEED EXISTS AS OF 2026-08-19, PARTIAL COVERAGE**. `scripts/betting_insider.py` / `GET :8001/insider/sharp-moves/{sport}` gives OPENING vs CURRENT Pinnacle prices for **mlb, nfl, nba, nhl** (96/96 MLB props carried Pinnacle open+current on the day it was wired; 15 had moved ≥5%). **Read Pinnacle's move, not the soft book's** — soft drift is position management, Pinnacle moving is the sharp signal. Negative move % = money came in on that side; positive = it drifted out. ⚠️ Still NO feed for **soccer or tennis**, and the pick ledger still stamps 0 closing odds (`ENABLE_CLV_CAPTURE` off) — so post-hoc 'did we beat the close' grading remains dark even where the pre-bet read now works. Original intent: Evaluate whether the current line is better or worse than it was 4-8 hours ago. If line moved heavily toward a team, ask: "Is value still here or did sharps already close the window?" If line moves AGAINST your logic without obvious reason, flag as SHARP_OPPOSITION — possible injury news missed.
5. **SCAN EVERY MARKET — PICK THE BEST TYPE (no auto-moneyline)** — ✅ **PARTLY ENFORCED IN CODE (2026-08-19)**: `/predict` returns a `market_ladder` — every market the model can price, ranked by win probability, each with the `min_odds` break-even price. **Bug fixed 2026-08-19: the ladder was built only inside the NBA/WNBA branch, so NFL, MLB and NHL returned NO ladder at all** and the engine could only ever answer with whichever spread the caller happened to ask about — the exact single-market failure this rule forbids. All margin sports now get ML + their sport's key alternate lines (`ALT_SPREADS`: NFL 3/7/10, basketball 5/10, MLB/NHL 1.5); period markets stay basketball-only because the independent-increments proxy behind them does not hold for football or hockey. Props and soccer derivatives still come from `/player-prop` and `/predict-soccer` — read the ladder, then still do the rest of this rule by hand: Do NOT default to the side/moneyline. Enumerate EVERY market for the matchup — moneyline/win, draw / double chance / draw-no-bet (soccer), spread/handicap (incl. alternates), totals over/under (incl. alternates), team totals, BTTS, period/quarter/F5 derivatives, AND the sport's niche PLAYER PROPS (use the sport skill's prop menu — NBA points/reb/ast/3PM, NFL pass/rush/rec yds, MLB Ks/HR/hits, NHL shots/saves/anytime goal, WNBA usage-spike props, soccer shots-on-target/cards/anytime scorer, tennis aces/total games, UFC method/round, F1 driver H2H/DNF/classified). Estimate each market's true win-prob from the sport's niche stats + simulation, compare it to that market's own devigged implied price, and take the SINGLE highest win-prob market that clears the value gate — whatever TYPE it is. A prop, total, or handicap can beat the side. **PROP SOURCING GUARD**: only float a prop when REAL player stats are in context; if the prop line is not on the live board, call it a "lean", never invent the number. If the main market is efficient (heavy juice, sharp action already priced in), the softer derivative/prop usually holds the cleaner edge.
6. **INJURY IMPACT QUANTIFIER**: Missing player = structural team change. NBA: high-usage star out → analyze usage increase for backup → backup's Over props are often highest EV in the game. MLB: high-leverage reliever pitched 2 nights in a row → assume unavailable → lean Over on 7th-9th innings total.

8. **SHARP CHECK (final step before any output)**: 
    - (a) CLV Check: Is this line better than 4hrs ago? 
    - (b) Correlation: Is this SGP statistically grounded or "perfect world" logic? 
    - (c) Derivative: Is there a softer market with cleaner EV? 
    - (d) Fragility: If one player gets hurt/foul trouble early, does the whole thesis collapse? If yes, reduce unit size to 0.5u.
9. **FLAG HIGH-RISK**: If a bet violates any rule above, label it [HIGH-RISK] and provide a PIVOT that aligns with statistical reality.
10. **CHAOS PASS + TIERED CARD (deterministic, no hallucination)**: The chaos engine (`scripts/chaos_engine.py`) runs on EVERY match with a favourite and returns a graded flag + DRAW SCORE, each carrying an `evidence[]` trail. Consume those numbers — never invent them.
    - **CHAOS-FULL** = heavy fav (≤1.50) the model says is overpriced + live dog → back the dog / X2 (Wild tier only, tiny stake).
    - **CHAOS-LITE** = mid fav (1.50–1.90) with an underpriced draw (model draw% > market draw%) → the draw (X) / Double Chance (Mild or Wild).
    - A chaos pick is only a PICK when it clears the value gate (Rule 1); otherwise it is a NOTE.
    - **DATA CONTRACT**: every probability cites a real input or the devigged price. Narrative (news/motivation) may nudge ±5% max and MUST name its source. Missing data → "unavailable", widen uncertainty, never fill with a guess.
    - **TIERED OUTPUT**: render the card in three sections sized by `scripts/staking.py` (70% Normal / 20% Mild / 10% Wild of bankroll). Each pick: market + price + one-line evidence + stake (units & $). Empty tier prints "PASS — no value today." `slate_weather` (CAGEY/OPEN/NORMAL) is a soft totals modifier only — NOT chaos.
11. **PARLAY DISCIPLINE — WIN-PROB FIRST, then data-backed (OBEY)**: WINNING MONEY is the focus, not max ROI. ⚠️ **The numbers below are a SNAPSHOT and drift — the linter does not read them.** `slip_linter._history_rois()` recomputes ROI live from `data/slips_raw.txt` on every call, so the CODE is always current even when this prose is not. Regenerate with `python3 scripts/analyze_slips.py`. Snapshot 2026-08-19 (135 deduped tickets, $1,828 staked, **net +$795, ROI +43.5%, hit rate 47%**) — **2–3 legs +51.0% (20/38)**, 4–6 legs +39.5% (19/45), 7+ legs +197.3% but only 2/12 (variance, not a lane), singles +29.2% (22/40).
    - **Default ticket = 2–3 legs. HARD CAP at 4. NEVER build 5+.** Fewer correlated legs beat long stacks every time.
    - **ANCHOR ON CHALK — do NOT auto-drop it.** The high-prob favourite (decimal <1.50, ~67%+) is the SAFEST leg; it CARRIES the ticket (rule 0). Build around 1–2 chalk anchors *that clear the value gate* — if a fav is no-value crushing juice (e.g. −511), take its handicap/total/correct-score to keep the win-prob without laying dead money (rule 1 · [[feedback_no_value_chalk]]). ⚠️ **2026-08-19 recheck: chalk-anchored TICKETS are running −15.3% (6/9)** — still a thin sample, but it does NOT currently support 'chalk is the safest leg'. Keep the structural rule (a lock carries a ticket) but stop quoting chalk as proven; the linter reads the live number either way.
    - **THE TRAP IS THE SOFT FAVOURITE (decimal 1.50–1.90, ~53–67%)** — a favourite, NOT a lock (a 1.64 at 61% still misses ~2 in 5; it is NOT a "coin-flip", which is 2.00/50%). **Max ONE per ticket**; two of them and the slip is a flip. This is where the MODEL failed on 2026-06-25: IT tagged Kecmanovic 1.78 + Navarro 1.66 as safe and faded the user's chalk — those two MODEL picks lost while every chalk leg the user had hit. The leak was the model's judgment, not the user's.
    - **Value/longshot (1.90–5.0)** = fine for the upside leg — the live record's best band (longshot 2.50–5.0: **+66.2% across 48 tickets**). **Lottery >5.0 is still cut by the linter on structure**, and note the record now reads +94.6% there (8/36) — a low-hit high-variance tail, NOT a lane to chase; 8 wins in 36 is exactly the shape that feels profitable right up until it isn't.
    - Combined ticket target ~ 1.8–8.0 decimal. A safe chalk combo that pays thin but WINS beats a fat longshot stack that misses — that is the whole point.
    - **ENFORCE, don't hope: run every proposed ticket through `scripts/slip_linter.py`** (or `POST /api/lint-slip` with `{legs:[{decimal,selection}]}`). It KEEPS chalk anchors, CAPS soft favourites at one per ticket (cuts the lowest-win-prob first; a /predict LEAN counts as a soft favourite), cuts lottery / 5+ stacks, cites real ROI per cut, surfaces each leg's pick_quality grade, and returns ACCEPT / TRIM / REJECT against the user's *live* record. Output the verdict + apply the trims before presenting any parlay. `/predict` auto-lints — surface the `lint` field and the per-leg LOCK/PICK/LEAN.

16. **DATA-FRESHNESS GATE — CHECK THE FEED BEFORE YOU TRUST THE MODEL (added 2026-08-19)**: a stale rating is not a smaller edge, it is a WRONG edge, and it fails silently. Real incident that motivated this rule: `fetch_tennis_ratings.py` had been 403ing against ESPN for weeks (ESPN's edge blocks browser-spoofed User-Agents), so tennis ranks sat frozen at 2026-07-18 while the engine kept pricing matches at full confidence; club-soccer ratings simultaneously predated the 2026-08-08 season start. Nothing anywhere flagged it at pick time.
    - ✅ **ENFORCED IN CODE ON BOTH PATHS (2026-08-19)** — `edge_api.freshness_guard()` on every `/predict` (`STALE` drops one grade, `SEASON_BOUNDARY` caps at LEAN, reason written into `quality_note`, `data_freshness` block attached), AND `bank_builder.apply_data_gate()` on the **day card** (`BET` -> `LEAN` with a `data_gate` note). Both paths matter: the card had its own verdict logic and consulted neither gate, so the same fixture could read LEAN from /predict and a full BET on the card you actually click. Two paths to one decision must not disagree — when you add a gate, grep for the OTHER path.
    - **Source death is a SEPARATE failure from stale data** — a file on disk just quietly ages while its upstream 403s, which is exactly how tennis froze. `scripts/feed_health.py` / `GET :8001/feed-health` probes all 9 upstreams and joins reachability to freshness, so a red line reads `DEAD (403) + 32d old` instead of a silent STALE. A daily 06:30 watchdog in server.ts logs `[FEEDS] ⚠️ UPSTREAM DOWN`, and the script exits non-zero for cron/CI.
    - `SEASON_BOUNDARY` still means the ratings describe a roster/league that no longer exists — lean market + context, and never present the model % as hard.
    - **Never add a `Mozilla/...` User-Agent to an ESPN call.** It is exactly what gets 403'd; urllib/requests/node defaults are served fine.

18. **PAYWALL PLACEHOLDERS ARE NOT DATA — VERIFY A FEED MEANS WHAT ITS NAME SAYS (added 2026-08-19)**: the failure mode is not a feed going down, it is a feed that keeps returning confident-looking numbers that mean nothing. Two live examples caught the day this rule was written, both from thebettinginsider.com:
    - Its `/public-betting` PAGE renders **every** split as exactly `50% / 50%` when logged out. That is the lock state, not a market read. Scrape it and you ingest "the public is perfectly split" on all 15 games.
    - Its `consensus_over_pct` field looks like public money and is not — it tracks a tiny Sleeper sample, and reads exactly `100` on 33/96 rows for that reason alone.
    - **Before wiring ANY new field, check its distribution, not one sample.** A value that is constant across rows (50/50), pegged at a boundary (0/100), or perfectly correlated with another field is a placeholder or an alias — treat it as `None`. Check the companion sample-size field; if there isn't one, assume the sample is too small.
    - **Free ≠ open.** Linemate and Betting Insider both paywall the website while leaving a JSON route unauthenticated; the reverse also happens. Probe the API before concluding a source is unusable — and never sign up for, or pay for, a source to work around this.
    - Prefer a feed that ERRORS over one that degrades to a plausible number. `scripts/linemate.py` and `scripts/betting_insider.py` both return `None` + a note rather than a filled-in guess; keep new fetchers to that standard.

20. **NAME THE MARKET EXACTLY — LOOK-ALIKE MARKETS ARE A MONEY LEAK (added 2026-08-19)**: books list markets whose LABELS are nearly identical and whose PROBABILITIES are nothing alike. A real ticket was built on Stake's "Hándicap de **Set** −1.5" after the engine had priced "−1.5 **games**": 58.7% vs 82.3% for the same player — a 24-point error, and the ticket came out 31.9% to win at −40% EV.
    - **−1.5 SETS in a best-of-3 means winning 2-0.** A 2-1 victory LOSES the bet: Sabalenka wins the match 86% but only wins 2-0 **58.7%** of the time, so she "wins and you lose" **27.5%** of the time.
    - ✅ **ENFORCED IN CODE**: `tennis_games_model.set_handicap()` is emitted on EVERY `predict()` call whether or not a handicap was requested, carrying `a_wins_match_but_loses_handicap` and a note naming the trap. The `/predict` tennis ladder now lists **24 markets** with both handicap families side by side and the set line spelled `home_-1.5_SETS_(must_win_2-0)`.
    - **Before pricing any pick, restate the market in full** — sport, side, market TYPE, line, and what has to happen for it to pay. If the user's wording is ambiguous ("−1.5", "handicap", "over"), ASK which market rather than assuming the one you already modelled. Getting this wrong is not a rounding error; it is a different bet.
    - Same family elsewhere: games vs sets, Asian vs European handicap, team totals vs match totals, "to win a set" vs "to win the match", 1H vs full game.

Post-fix bias: ATP **+0.13**, WTA **+0.06**.
    - **Money impact, on the actual losing bet**: OVER 21.5 went 70.2% → **52.7%**, EV at the 1.52 taken went **+6.7% → −19.9%**, min-odds floor 1.99. The calibrated engine REFUSES that bet.
    - **The general rule**: a model that is directionally sensible can still be systematically off by a constant, and that constant never shows up in a single pick — it shows up in the P&L. Backtest every probability the engine emits against settled results, split by the format actually bet, and persist the correction to a file the model reads so re-running the fit updates the engine.
    - **Split the sample by what you actually bet.** The first pass pooled Grand Slam best-of-5 with best-of-3 and read "no bias" — bo5 runs ~28 games vs bo3's ~21, and mixing them hid a 2-game error. Use the source's own format column, never infer it from the set count (a 3-set match is bo3 OR a bo5 won in straight sets).

22. **A BACKTEST IS ONLY AS HONEST AS ITS POINT-IN-TIME DATA (added 2026-08-21)**: rule 21 says backtest everything. This is the trap waiting on the other side. `data/all_ratings.json` holds ONE ranking snapshot (stamped 2026-08-19). Scoring past matches with it is LOOKAHEAD — a player who climbed during the season is over-rated for every earlier match they played.
    - **The tell is a bias that FLIPS SIGN between adjacent years.** The tennis win-prob backtest read ATP 2025 **+9.9 over-confident** and ATP 2026 **+0.0 perfect**; WTA 2025 **+6.5 over** and WTA 2026 **−7.0 under** — on ~500 matches each. A real model property does not reverse like that. What was being measured was how far the ratings snapshot post-dates the match, not the model. `tennis_winprob_backtest.py` is kept (the harness and leakage guard are right) but stamped **INVALID** in its own output.
    - **Before trusting any backtest, ask three questions**: (a) is every input as-of the match date, or a current snapshot? (b) does the result hold the same SIGN across independent years/tours/leagues? (c) is it flat across the dimension a data artefact would concentrate in? The totals calibration (rule 21) passes all three — same sign both tours both years, flat across match imbalance — so it stands with the caveat stated in its own docstring. The win-prob one fails (a) and (b), so it was discarded rather than shipped.
    - **Leakage guard, always**: results files store Winner/Loser. Asking a model about "the winner" makes the outcome 100% by construction. Order the two sides DETERMINISTICALLY (alphabetically) before predicting.
    - **Split by the format actually bet** and use the source's own format column — never infer it (rule 21).

23. **THE TENNIS RANK MODEL IS NOW MEASURED — AND THE ARCHIVE THAT MEASURES IT ONLY EXISTS GOING FORWARD (added 2026-08-21)**: rule 22 said the win-prob backtest was invalid for want of point-in-time ranks. `scripts/fetch_tennis_rank_history.py` now archives weekly ATP/WTA snapshots to `data/tennis_rank_history.json`, and `tennis_pit_backtest.py` prices every match with the ranking that stood **on or before the day it was played**.
    - **Measured, valid, 1,507 best-of-3 matches**: ATP **Brier 0.2272** (n=696), WTA **Brier 0.2169** (n=811), both against a 0.25 coin-flip. Favourite-side calibration ATP **+1.7**, WTA **−1.0**. **The model has real skill and is broadly well calibrated** — the earlier "all six favourites read short" worry was the invalid snapshot backtest talking, not the model.
    - ⚠️ **NO calibration correction is applied, deliberately.** The 70-80% buckets look badly off in OPPOSITE directions (ATP predicted 74.6% → actual 59.0%, z=+2.79; WTA predicted 75.0% → actual 88.7%, z=−2.49) — but twelve buckets were tested across two tours, so **~1 nominally-significant result is what noise looks like**. Neither clears the Bonferroni threshold (|z| > 2.87), so both corrections are ZEROED in code. Revisit once the archive is deeper; do not quote these gaps as findings.
    - **ESPN serves only a ROLLING WINDOW of ranking weeks** (verified: 2026 weeks 11-32 resolve, week 10 and all of 2025 are already 404). This history **cannot be back-filled** — it exists only if captured as it goes past, so the archiver runs inside the fortnightly tennis refresh. Missing a few months of runs permanently costs those weeks.
    - **A 200 is not proof you got what you asked for.** `/rankings/1` under the WTA league path returns HTTP 200 carrying the **ATP** ranking — the id is 1 for ATP and 2 for WTA. A hardcoded 1 silently filled the WTA archive with men's players and was only caught because the WTA backtest resolved zero competitors. The fetcher now DISCOVERS the id from the index and raises if the payload's own `shortName` disagrees with the tour asked for. Verify identity in the payload, not the status code.

24. **SOCCER TOTALS ARE MEASURED AND CLEAN — a negative result worth keeping (added 2026-08-21)**: after the tennis games-total model turned out to run 1.7-2.2 games long (rule 21), over/under goals got the same treatment — same shape of market, the user's number-one sport, never previously checked.
    - **`scripts/soccer_totals_backtest.py`, walk-forward, 1,311 games**: ratings refit monthly with `fit_club_ratings.build(as_of=)`, so an April game is priced by an April-1 fit that has not seen it. **Mean bias −0.012 goals.** Over 1.5 / 2.5 / 3.5 all inside noise (z = −0.81, −1.76, +0.08). **No correction applied**, and `data/soccer/totals_calibration.json` records `applied: false` with the reasoning rather than silently storing a zero.

Ligue 1 shows the largest per-league bias (+0.24 goals, z=1.96) and still does not clear the Bonferroni bar across the 8 tests run (3 lines + 5 leagues, z > 2.73) — so it moves nothing.
